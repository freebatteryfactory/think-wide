## The gap this closes

After the draft, a successful WorkOS login still left every Convex handler answering
`unauthenticated`: the browser's Convex client was a bare `ConvexProvider`, so nothing gave
it the user's token. Now, in identity mode `workos`, `src/integrations/convex/provider.tsx`
mounts `ConvexProviderWithAuth` with `useWorkOSConvexAuth`
(`src/integrations/workos/convex-auth.ts`).

### Installed APIs inspected (not documentation)

`@workos/authkit-tanstack-react-start` 0.11.1, `./client` export:

- `dist/client/index.d.ts`: exports `AuthKitProvider`, `useAuth`, `useAccessToken`,
  `useTokenClaims`, `useRecentAuth`, `Impersonation`, `getAuthAction`. There is **no**
  standalone `getAccessToken` export; it is a member of what `useAccessToken()` returns.
- `dist/client/AuthKitProvider.d.ts`: `useAuth(options?: { ensureSignedIn?: false }): AuthContextType`.
- `dist/client/types.d.ts`: `AuthContextType` has `user: User | null`, `loading: boolean`,
  `signOut(options?: { returnTo?: string }): Promise<void>`, among others.
  `UseAccessTokenReturn` is `{ accessToken: string | undefined; loading: boolean; error: Error | null; refresh(): Promise<string | undefined>; getAccessToken(): Promise<string | undefined> }`.
- `dist/client/useAccessToken.js`: `getAccessToken` and `refresh` are `useCallback(..., [])`
  (stable) and both return `undefined` when there is no user. `getAccessToken` reuses the
  cached token unless it is near `exp`; `refresh` always asks the server.
- `dist/client/AuthKitProvider.js` and `tokenStore.js`: the browser obtains auth state and
  tokens through the package's server functions, from the encrypted session cookie.
  **The browser does not need `WORKOS_CLIENT_ID`**, and no `VITE_WORKOS_*` variable exists.
  The client id appears only in the redirect URL the server builds.

`convex` 1.46.0, `dist/esm-types/react/ConvexAuthState.d.ts`: `ConvexProviderWithAuth`
takes `useAuth: () => { isLoading: boolean; isAuthenticated: boolean; fetchAccessToken(args: { forceRefreshToken: boolean }): Promise<string | null> }`.
`dist/esm/react/ConvexAuthState.js` re-runs `client.setAuth` whenever `fetchAccessToken`
changes identity, so the adapter keeps it stable (dependencies: user id and the two stable
AuthKit callbacks).

### Adapter behavior

- `isLoading` = AuthKit `loading`. `isAuthenticated` = AuthKit has a user. Convex still
  verifies the token itself before it reports authenticated or gives a handler an identity.
- `forceRefreshToken: true` calls `refresh()`; `false` calls `getAccessToken()`.
- Signed out: resolves `null` without calling AuthKit. A user but no token, or a thrown
  refresh: resolves `null`. There is no substitute principal on any path.
- The failure log line is a fixed string: no token and no upstream error text.

## Identity mode is explicit, in two places

| Variable | Read | Effect of `workos` | Default |
|---|---|---|---|
| `VITE_THINK_WIDE_IDENTITY` | build time, inlined in the browser bundle | mounts `AuthKitProvider` + `ConvexProviderWithAuth`, shows the sign-in affordance | `none` |
| `THINK_WIDE_IDENTITY` | server process start | installs `authkitMiddleware()`, enables `/api/auth/sign-in` and `/api/auth/callback` | `none` |

Only the exact string `workos` enables either. Both are mode names, never credentials. With
`none`, the app is what main shipped before I01: bare provider, handlers answer
`unauthenticated`, no sign-in link, AuthKit never called. Neither switch can grant access:
Convex authorizes from a verified token only. If the two disagree, the server logs one
`Identity mode mismatch` line and sign-in does not work; pages still render.

The Convex deployment is configured separately and by an operator: `WORKOS_CLIENT_ID` must be
set **on the Convex deployment**, and that deployment must not be `local-demo`, or
`convex/auth.config.ts` will not trust the WorkOS issuer. A `local-demo` backend rejects
WorkOS tokens by design, so a person can be signed in to AuthKit and still see
`unauthenticated` from Convex there. That is correct behavior, not a bug to work around.

## Regression found in the draft and fixed

Observed on this branch before the fix (draft merged with main, production build without
`VITE_CONVEX_URL`, no `WORKOS_*` in the environment): `/` **500**, `/workshop` **500**, with
`AuthKit configuration error ... WORKOS_CLIENT_ID is required` (and the other three names)
in the server log. `authkitMiddleware()` validates its configuration on the first request
and throws, so every page of an unconfigured deployment failed.

Fix: `src/start.ts` installs the AuthKit middleware only when `THINK_WIDE_IDENTITY=workos`;
the two AuthKit routes answer 404 otherwise (`src/server/auth/workos.ts`).

## Sign-out: what it does and does not do

The affordance calls the package's documented client sign-out, `useAuth().signOut()`. In the
installed code (`dist/client/AuthKitProvider.js`, `dist/server/server-fn-bodies.js`,
`authkit-session` `AuthService.signOut`) that clears the encrypted session cookie through
the AuthKit middleware and sends the browser to the WorkOS logout URL for that session.

It does **not** revoke an access token that was already issued. Such a token stays valid,
and Convex keeps accepting it, until its `exp` (reported lifetime: 300 s). Anyone who copied
it can use it for that window. The short lifetime is the only mitigation; there is no claim
of instant revocation. An open Convex websocket stays authenticated until the page
navigates away (sign-out does navigate) or the token expires. Sign-out in a browser: NOT RUN.

## Doubts and open decisions (not papered over)

- **No `aud` check.** Trust rests on the exact issuer match, which embeds our client id.
  Any access token WorkOS issues under that client id is accepted by Convex, whatever it
  was issued for. Whether the MCP profile shares this issuer is still open (issue #17); if
  it does not, one person is two Convex principals.
- **Topology.** In mode `workos` the browser talks to Convex directly with the user's
  token. Issue #17 raised keeping Convex private behind the app server (I04). This ticket
  does not decide that; policy is in the Convex functions either way (decision 0002).
- **The access token is readable by page JavaScript.** That is how `useAccessToken` works
  and what Convex's browser client requires. An XSS on this origin could read it for up to
  its lifetime.
- **Queries issued before AuthKit resolves the session** run unauthenticated first. The UI
  uses reactive `useQuery`, which Convex re-runs once auth is set; this was reasoned from the
  installed `ConvexAuthState.js`, not observed in a browser.
- **Two switches can disagree.** Logged once, fails safe (no sign-in), but it is an operator
  footgun. A single runtime switch would need the browser mode delivered by the server
  instead of at build time; not done here.
- `src/server/auth/verify-token.ts` (MCP/HTTP edge verification, listed for I01 in
  `docs/REPO_MAP.md`) is **not** part of this change.
